Date: 2026-05-07  
Epic revue: Epic 4 - Table resiliente et diagnostic (FR3, FR15, FR16, FR28, FR29, FR30)

## 1) Revue Epic 4

### Resultat global

- Stories terminees: `4-1` a `4-5` (100%).
- Parcours resilience livres: sortie volontaire avec transfert hote et regles de partie (`leave`), arrivee en cours avec statut joueur / spectateur et garde-fous API (`join`), reprise de session cookie sans bump parasite (`session_resumed`), reconnexion WebSocket avec degrade et banniere de synchro, absence hote sur le flux temps reel avec grace et transfert passif documentes cote serveur et UI, correlation diagnostic pour support (`correlation_id`, `diagnostic_ref`, `session_fp`, logs evenements cles).
- Qualite: pytest API et Vitest / typecheck web au vert sur les increments livres ; README enrichi avec les contrats Epic 4.

### Ce qui a bien fonctionne

- **Servir comme source de verite** `GET .../state` + polling pour rattraper les coupures, tout en gardant le WS pour la vivacite — la story 4.3 s'appuie sur ce dualisme sans inventer un second modele d'etat.
- **Regles serveur explicites** pour spectateur (`spectator_action_forbidden`), pour la reprise cookie (pas de `participant_join` si resume), pour le depart (`participant_left`, transfert hote, rollback lobby si quorum insuffisant).
- **Instrumentation progressive**: comptage WS par participant avant la logique « hote absent », puis journal `mousquetaire.support` et refs utilisateur sans casser les contrats REST existants.
- **Tests qui ont force la precision**: transfert hote apres grace avec `HOST_WS_ABSENCE_GRACE_MS <= 0` pour rester deterministe sous `TestClient` ; attention aux fermetures de sockets dans les asserts pour ne pas redeclencher la logique d'absence.

### Ce qui a coince / points d'attention systeme

- **Couches async / threads**: transfert hote apres grace en prod via `threading.Timer` + `asyncio.run(broadcast...)` pour eviter les fuites de taches sous Starlette TestClient — pattern correct mais a documenter pour tout futur timer hors boucle d'event-loop.
- **`App.tsx` toujours volumineux**: reconciliation polling + WS + bannieres (sync, spectateur, grace hote, diagnostic) — le risque signale en retro Epic 3 persiste ; Epic 5 gagnerait a extraire des hooks ou modules dedies si le solo ajoute des etats.
- **Correlation navigateur**: les WebSockets ne portent pas d'en-tetes HTTP ; la correlation passe par query `correlation_id` — coherent mais a rappeler dans toute doc operateur.
- **Couverture observabilite**: logs INFO utiles pour support MVP ; pas encore d'agregation centralisee, pas de niveaux DEBUG fines pour le spam potentiel sur mutations jeu frequentes.

### Lecons apprises

1. Les scenarios **« absence passive »** (fenetre de grace, annulation si reconnect) demandent des **invariants de test** stricts (qui ferme quelle socket et quand) pour eviter les faux positifs sur le transfert hote.
2. **FR30** peut etre honore sans stack imposee au rapport utilisateur: **`diagnostic_ref`** + `room_id` dans les logs + en-tete correlation suffisent pour une premiere correlation exploit par grep.
3. **Messages utilisateur** (FR29) pour l'hote absent se pretent bien a une combinaison **banniere persistante pendant la grace + toasts** pour les transitions ponctuelles — garder ce pattern pour d'autres etats transitoires futurs.

### Dette technique restante (non bloquante cloture Epic 4)

- Modulariser le client (`App.tsx`) pour isoler transport temps reel, refs diagnostic et bannieres.
- Renforcer optionnellement le lien **cookie-session ↔ mutations** pour reduire la surface « participant_id fourni seul » (deja identifie en Epic 3).
- Persistance durable et correlation multi-instance hors scope MVP actuel.

Date: 2026-05-07  
Epic revue: Epic 3 - Boucle de jeu synchrone (tours, indice, grille, revelations, fin de manche, scores, feedback risques, reversibilite P0)

## 1) Revue Epic 3

### Resultat global

- Stories terminees: `3-1` a `3-8` (100%).
- Boucle nominale livree bout-en-bout: WebSocket + `turn_version`, indices, selection grid, revelation synchronisee, RoundResolution avec beat, scores et fin de partie, retours UX sur actions a risque (FR31), retrait d'indice par l'auteur sous gardes serveur (FR32 dans la limite P0).
- Qualite: lint / typecheck / tests verts sur les derniers increments ; README enrichi avec les contrats API des slices jeu.

### Ce qui a bien fonctionne

- **Serveur autoritatif + envelope `{ type, payload, version }`** comme pivot commun REST et WS: meme famille de champs dans les snapshots reduit la derive cognitive entre polling et temps reel.
- **Garde-fous API par phase et par role** (indice, toggle, reveal, tour suivant, reprise manche): les erreurs `detail.error_code` sont stables et exploitables cote UI (toasts + zones inline).
- **Composition incremental**: RoundResolution puis scoring partie puis friction utilisateur (3.7) puis reversibilite ciblee (3.8) sans tout recomposer la machine d'etat en une seule story.
- **Tests API sur transitions**: exemple recent du retrait d'indice (succes, mauvais joueur, blocage apres interaction grille).

### Ce qui a coince / points d'attention systeme

- **Complexite du client**: `App.tsx` concentre reconciliation polling + WS, versions de tour, et regles UX — risque de regressions si Epic 4 ajoute reconnexion et etats transitoires sans extraction modulaire.
- **Dedup notifications**: UX-DR6 reste partiellement appliquee (versions et filtres d'evenements) ; la coherence toast vs WS demandera une passe si le nombre d'evenements augmente (Epic 4).
- **Securite identite**: comme note en Epic 2, les mutations sensibles reposent encore sur `participant_id` fourni par le client sans lien fort cookie-session — acceptable MVP mais sensible des qu'on ouvre rejoin / deconnexion (Epic 4).
- **Perf / charge**: WebSocket en memoire process, pas de test de charge formalise — aligne avec V1 mais a garder en tete pour NFR-P1.

### Lecons apprises

1. Les **champs derivees** (`clue_withdraw_allowed`, scores, messages de fin) doivent rester **calculables ou exposes dans `GET .../state`** pour que l'UI desactive les actions sans deviner la logique metier.
2. Les **flags de granularite fine** (`clue_selection_touched` vs simple liste selectionnee) permettent des regles produit nuancees (ex. deselection sans rouvrir le retrait d'indice).
3. Documenter **chaque endpoint de jeu** dans le README au fil de l'eau evite la derive entre contrat reel et onboarding contributeurs.

### Dette technique restante (non bloquante cloture Epic 3)

- Modulariser l'etat jeu cote front (hooks ou module dedie) avant d'empiler Epic 4.
- Renforcer optionallement la strategie UX-DR6 (cles de dedup explicites par operation).
- Lier session HTTP et participant pour les mutations (suite logique Epic 2 / Epic 4).
- Persistance et snapshots durables (Firestore) toujours hors scope immediat du code actuel.
